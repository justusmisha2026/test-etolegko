## Цель и границы

Создать приложение на Python для управления кампаниями через Keitaro: пользователь задаёт параметры новой кампании либо открывает существующую и меняет состав её офферов. Проверяющий должен воспроизвести запуск и убедиться в корректности состояния Keitaro после действий приложения. Основания: SRC-02, SRC-03, SRC-12.

В объём будущей реализации входят форма создания, интерфейс редактора, интеграция с Admin API, хранение необходимых локальных данных через SQLAlchemy, миграции, обработка ошибок и инструкция запуска. Конкретное назначение локальной БД предложено ниже и не задано исходником.

Не входят в объём текущего аудита: написание приложения, создание или изменение кампаний, офферов, групп, источников, доменов и ключей; публикация репозитория; отправка результата рекрутеру. Не заявлены как функции будущего приложения: собственный рекламный трекер, создание глобальных офферов, управление пользователями Keitaro, весь интерфейс AdRobot из видео, автоматизация рекламы и расчёт бизнес-метрик без уточнения их состава.

### Подтверждённые ограничения сдачи

По SRC-03 требуются FastAPI и SQLAlchemy; выбор фронтенда свободный. Кампании следует называть с префиксом `test_фамилия_`. Нужен публичный GitHub-репозиторий с понятным README по миграциям и запуску. В форме сдачи есть обязательное описание использования ИИ и необязательный скринкаст длительностью до трёх минут. ## Требования и критерии приёмки

Требования с пометкой «источник» перенесены из материалов задания. Пометка «вывод аудита» обозначает конкретизацию для проверяемости и сохранности данных; её нельзя выдавать за дословное условие рекрутера. Детали, зависящие от Q-01 и Q-02, окончательно не определены.

### REQ-01 Входные данные новой кампании

**Основание:** источник SRC-02; валидация — SRC-12 и вывод аудита. **Компоненты:** UI, схемы FastAPI, клиент Keitaro.

Принимать название кампании, гео-код одной страны и ID существующего оффера Keitaro. Отдельно определять домен, группу и источник по REQ-03. Проверять обязательность значений, тип ID и допустимость страны по подтверждённому контракту стенда. Не подменять ID отсутствующего оффера произвольной записью.

**Приёмка AC-01:** корректные значения доходят до операции создания без изменения смысла; пустое имя, отсутствующая страна, неверный тип ID и недоступный оффер приводят к понятной ошибке, а не к сообщению об успехе. Конкретные ограничения длины и допустимые коды фиксируются после Q-02.

### REQ-02 Создание и маршрутизация

**Основание:** источник SRC-02; порядок применения — вывод из SRC-08. **Компоненты:** сервис создания, API-клиент, кампания и потоки Keitaro.

Создавать одну кампанию с двумя потоками. Первый принимает трафик указанной страны и перенаправляет на Google. Второй направляет оставшийся трафик на указанный оффер. Последняя формулировка конкретизирует назначение второго потока; выбор его технического типа описан в DEC-01.

**Приёмка AC-02:** повторное чтение созданной кампании подтверждает два потока и заданные назначения. Сценарии для указанной страны и другой страны выбирают соответствующие направления. Проверить отдельно повторный визит и неизвестную страну; политика привязки посетителя не должна нарушать основное правило. Предлагаемый точный адрес Google — `https://google.com/`, показанный также в SRC-04; тип HTTP-редиректа исходником не задан.

### REQ-03 Домен, группа и источник

**Основание:** источник SRC-02; явный выбор — предложение DEC-02. **Компоненты:** форма, справочники, сервис создания.

У кампании должны быть настроены домен, группа и источник Keitaro. Брать допустимые записи из API и передавать их идентификаторы. Не создавать новые записи справочников автоматически.

**Приёмка AC-03:** после создания чтение кампании подтверждает выбранные связи; исчезнувшая или недоступная запись вызывает ошибку. При пустом справочнике UI объясняет невозможность завершить создание. Фиксированные ID в исходнике не заданы.

### REQ-04 Загрузка и изменение состава офферов

**Основание:** источник SRC-02 и вывод AUD-05. **Компоненты:** редактор, сервис редактирования, привязки офферов к потокам.

Открывать существующую кампанию и получать её актуальную структуру. Добавлять существующий оффер в редактируемый поток и удалять его привязку из этого потока. Глобальный объект оффера не удалять. Поток выбирается явно. Редактировать можно поток с `schema=landings`, уже содержащий офферы, в кампании с собственным настроенным префиксом; остальные кампании доступны только для просмотра.

**Приёмка AC-04:** после добавления/удаления состав в приложении совпадает с повторно прочитанным составом Keitaro. Глобальный оффер и его привязки в других кампаниях сохранены. Дубли и удаление последнего активного оффера запрещены (SRC-15). Повторное сохранение без изменения состава не пересчитывает доли; повтор с устаревшей ревизией возвращает конфликт.

### REQ-05 Числа и поведение редактора

**Основание:** исходные SRC-02/SRC-04 и уточнение SRC-15, заменяющее неподтверждённую часть правил видео. **Компоненты:** расчёт долей, состояние редактора, числовые поля API.

Доли рассчитываются автоматически целыми процентами с суммой активных долей 100%. Ручное изменение процентов не предусмотрено. Stats/Trends исключены из текущего объёма по SRC-15.

**Конкретизация реализации:** для `n` активных офферов вычислять `q, r = divmod(100, n)`, первым `n-r` назначать `q`, последним `r` — `q+1`. Новый оффер добавляется в конец; при удалении порядок оставшихся сохраняется. Выключенные привязки сохраняют состояние и при перерасчёте получают 0%. Локальный предел — 100 привязок, чтобы активная доля оставалась положительной. Эти детали округления и границ являются явным техническим решением, а не установленными фактами о видео.

**Приёмка AC-05:** `[A:100] → добавить B → [A:50,B:50] → добавить C → [A:33,B:33,C:34] → удалить B → [A:50,C:50]`. Проверить запрет дубля и удаления последнего активного оффера. Для 1–100 активных офферов сумма — 100, минимальная доля не меньше 1, разница между максимальной и минимальной не больше 1. Открытие без изменения состава сохраняет фактические доли Keitaro.

### REQ-06 Сохранение незатронутых данных

**Основание:** вывод AUD-05 и AUD-08. **Компоненты:** клиент API, сервис редактирования.

Изменять только согласованные привязки и связанные с ними доли. Сохранять Google-поток, фильтры, порядок потоков, домен, группу, источник, прочие потоки и настройки, которые действие пользователя не затрагивает.

**Приёмка AC-06:** сравнение снимков до и после показывает только ожидаемые изменения. Проверить кампанию с дополнительными настройками и использование одного оффера несколькими кампаниями. Полную замену массива привязок применять только после проверки семантики API.

### REQ-07 Актуальное состояние и конфликт редактирования

**Основание:** вывод AUD-08. **Компоненты:** UI, сервис редактирования, локальные данные.

Отображать состояние, полученное из Keitaro; успешное сохранение подтверждать повторным чтением. При обнаруженном изменении редактируемых данных с момента загрузки не перезаписывать их молча, а предложить обновление формы. Не маскировать ошибку записи изменением только локальной БД.

**Приёмка AC-07:** изменение данных через админку между загрузкой формы и сохранением обнаруживается в проверяемом сценарии. Если API не поддерживает условную запись, документировать оставшееся окно гонки; локальная блокировка не считается защитой от всех внешних клиентов.

### REQ-08 Ошибки, повторные действия и частичное создание

**Основание:** вывод AUD-07, требования обработки ошибок SRC-12. **Компоненты:** сервисы операций, UI, клиент API, журнал операций.

Различать ошибку ввода, отказ доступа, отсутствие объекта, недоступность зависимости и неопределённый результат записи после тайм-аута. Успех создания означает наличие всей конфигурации из REQ-02 и REQ-03. При частичном результате показывать известный ID и незавершённый шаг. Не повторять создающий запрос автоматически, если предыдущий мог выполниться.

**Приёмка AC-08:** контролируемый отказ на каждом шаге не приводит к ложному успеху; двойное нажатие не создаёт повторную операцию в проверяемом сценарии; повтор после тайм-аута сначала сверяет состояние. Механизм восстановления из DEC-03 проверяется отдельно. Удаление частично созданного объекта допускается только после проверки его принадлежности текущей операции.

### REQ-09 Секреты и конфигурация

**Основание:** схема Admin API SRC-06; вывод аудита. **Компоненты:** серверная конфигурация, HTTP-клиент, логи.

Хранить API-ключ на серверной стороне; не включать его в фронтенд, репозиторий, README, ответы приложения и логи. Адрес Keitaro и параметры доступа задавать конфигурацией. Использовать только необходимый ключ существующей учётной записи; создание или расширение прав ключей не входит в задание аудита.

**Приёмка AC-09:** пример конфигурации содержит только пустые значения или понятные заглушки; клиентский код и диагностические сообщения не содержат ключа. Приложение сообщает о нехватке конфигурации до выполнения операции.

### REQ-10 Стек и качество кода

Комментарии в коде не добавлять; необходимые docstring публичных функций и классов допустимы. Конкретные версии зависимостей выбрать и зафиксировать при реализации, после проверки их совместимости.

**Приёмка AC-10:** интеграцию Keitaro можно подменить в тестах; расчёты проверяются без сети; транспортный слой не содержит отдельной копии бизнес-правил; запуск использует зафиксированные зависимости.

### REQ-11 Имена и ограничения тестового стенда

**Приёмка AC-11:** создаваемое имя соответствует настроенному префиксу; инструкция явно задаёт, какие объекты можно проверять и очищать. Значение префикса исполнителя задаётся конфигурацией, не переносится в этот документ как персональная информация.

### Контракты интеграции, которые необходимо зафиксировать

Для клиента нужны операции чтения кампании и потоков, создания кампании и двух потоков, изменения привязок офферов, чтения справочников и проверки итоговой структуры. По общей документации Admin API используется префикс `/admin_api/v1/`, авторизация через `Api-Key` либо Bearer. Публичное руководство описывает PUT как обновление переданных полей; это не доказывает семантику вложенного массива офферов. Основание: SRC-06.

Опубликованная схема SRC-07 подтверждает следующие маршруты относительно `/admin_api/v1`. Запросы к этим маршрутам на тестовом стенде во время аудита не выполнялись.

| Назначение | Метод и маршрут |
| --- | --- |
| Список кампаний | `GET /campaigns`, параметры `offset`, `limit` |
| Создание кампании | `POST /campaigns` |
| Чтение / обновление кампании | `GET /campaigns/{id}`, `PUT /campaigns/{id}` |
| Потоки кампании | `GET /campaigns/{id}/streams` |
| Создание потока | `POST /streams` |
| Чтение / обновление потока | `GET /streams/{id}`, `PUT /streams/{id}` |
| Справочники | `GET /offers`, `GET /domains`, `GET /traffic_sources`, `GET /groups?type=campaigns` |
| Доступные фильтры и действия | `GET /stream_filters`, `GET /streams_actions` |

Значимые детали схемы, которые следует сохранить в адаптере интеграции:

- `CampaignCreateRequired` требует `alias` и `name`. В описании ответа `Campaign.alias` допускается пустое значение для автогенерации; допустимость пустого `alias` при создании следует проверить, а не выводить из схемы ответа.
- `CampaignRequest` содержит `domain_id`, `group_id`, `traffic_source_id`. Для `group_id` запрос описывает строку, ответ `Campaign` — целое число.
- `StreamRequest` требует `campaign_id`, `schema`, `type`, `name`, `action_type`; `StreamObject.type` допускает `forced`, `regular`, `default`, а `schema` — `landings`, `redirect`, `action`.
- `OfferStreamRequest` требует `offer_id` и целочисленный `share`, описанный как процент трафика. Это поле привязки, а не вес потока `weight`.
- `FilterStreamRequest.payload` описан массивом строк, а `Filter.payload` в ответе — строкой. Преобразование необходимо подтвердить на реальных обезличенных примерах.
- `Stream` содержит `action_payload`, но `StreamObject`, используемый запросами создания/изменения, его не перечисляет. Это не доказывает запрет поля сервером; точный способ задания Google URL остаётся частью Q-02.

До реализации требуется сверить эти детали со схемой или обезличенными примерами установленного API, доступными действиями/фильтрами и правами ключа. Отдельно проверить замену массива офферов, ошибки и пагинацию; не распространять параметры списка кампаний на все справочники без доказательств.

Чистую логику и отказы сначала проверять с подменой API. Чтение и запись на реальном стенде разделять. Симуляция Keitaro не отправляет реальный трафик, но может отражаться в журнале кампании; применять её только на предназначенных для проверки объектах (SRC-11). Текущий аудит симуляции и кликов не выполнял.

Для нового локального приложения потребуется начальная миграция его собственной БД. Миграция данных Keitaro не предусмотрена. Откат локальной транзакции не отменяет уже выполненную запись в Keitaro; восстановление должно учитывать ID и фактическое состояние внешних объектов. Логи будущего приложения должны связывать ошибку с операцией, не раскрывая секретов. Автоматическая очистка чужих данных исключена.

**Проверки реализации:** автоматические тесты находятся в `tests/`; запуск и миграции описаны в [README](../../README.md). Проверены сценарии создания, автоматических долей, конфликтов, частичных отказов, восстановления и сохранения журнала после перезапуска. Локальный демонстрационный интерфейс пройден через браузер. Проверки стенда описаны отдельно в SRC-17; они не заменяют проверку фактической маршрутизации.

**Открытая ручная приёмка:** выбранная страна, другая страна, неизвестная страна и повторный визит в симуляторе Keitaro. Я не могу подтвердить эти сценарии как пройденные: в ходе реализации проверялась конфигурация потоков, а клики и симуляции не выполнялись.

Для симуляции была предпринята попытка повторного включения собственной кампании. Автоматическая проверка разрешений отклонила действие из-за возможности реальной маршрутизации без отдельного подтверждения пользователя; команда не выполнялась. Эта проверка остаётся ожидающей подтверждения, см. SRC-17.

**Файлы:** FastAPI, SQLAlchemy и миграции, клиент Keitaro, интерфейс, автоматические тесты, зафиксированные зависимости и инструкция запуска созданы. Публикация репозитория и отправка рекрутеру не выполнялись. API-ключ хранится только в исключённом из Git локальном `.env`; пароль в проект не включён.

Новая инструкция SRC-14 разрешила реализацию и интеграционные проверки, поэтому прежние ограничения «не входит в текущий аудит» относятся к завершённому этапу аудита. Новые ключи, глобальные офферы и общие справочники не создавались и не изменялись. Собственная тестовая кампания после проверки оставлена выключенной.
